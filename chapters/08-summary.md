# 第8章 まとめ

第1〜7章で、6 種類の設定を 1 つずつ作り、`~/.claude/` に導入した。この章では、それぞれをいつ使うかを振り返る。

## 1. 使い分けの早見表

| やりたいこと | 使うもの | 章 |
|---|---|---|
| どんな作業でも守ってほしい方針（答え方・確認の仕方） | CLAUDE.md | 第1章 |
| 特定の種類のファイルを扱うときだけのルール | rules（`paths` あり） | 第2章 |
| 決まった手順・説明の形を、呼び出して使いたい | skills | 第3章 |
| たくさん読む作業を任せて、結論だけ欲しい・先入観なく見てほしい | agents | 第4章 |
| 特定のコマンドやファイルの読み取りを、確認・禁止したい | permissions | 第5章 |
| 条件付きで確認・禁止したい、ツールを使った後に処理を動かしたい | hooks | 第6章 |
| どのプロジェクトでも同じ設定を使いたい | `~/.claude/` に置く | 第7章 |

迷ったときは、次の順に考える。

```text
絶対に守らせたい？
  ├─ はい ─ コマンドやファイルのパターンで判定できる？
  │          ├─ はい → permissions
  │          └─ いいえ（条件付き・後処理） → hooks
  └─ いいえ（Claude に判断させてよい）
        ├─ いつも守ってほしい → CLAUDE.md
        ├─ 特定のファイルのときだけ → rules
        ├─ 呼び出して使う手順・説明の形 → skills
        └─ 任せて結果だけ欲しい → agents
```

## 2. お願いと強制

| | お願い | 強制 |
|---|---|---|
| 種類 | CLAUDE.md・rules・skills・agents | permissions・hooks |
| 誰が判断するか | Claude（AI）が読んで従う | Claude Code（プログラム）が判定する |
| 守られるか | 守られないことがある | 必ず効く |
| トークン | 使う（Claude に渡すため） | 基本的に使わない |
| 得意なこと | 方針・好み・状況に応じた判断 | 確実に止める・確認する・毎回同じ処理をする |

### 二重に守る

大事なことは、お願いと強制の**両方**に書く。

```text
例: .env を読ませない

  CLAUDE.md（お願い）     「.env は読まない」
     → ふだんは、Claude が最初から読もうとしない
     │ もし読もうとしたら…
     ▼
  permissions（強制）     "Read(**/.env)" を deny
     → Read ツールでの読み取りを必ず止める
```

お願いだけだと守られないことがある。強制だけだと、Claude はやろうとして止められ、そこで作業が止まる。両方に書くと、Claude は最初からやろうとせず、万が一やろうとしても止まる。

## 3. 既知の制限

この教材で作った設定には、次の抜け穴がある。知ったうえで使う。

| 制限 | 起きること | 対策 |
|---|---|---|
| Write の hook は、Bash でのファイル作成では動かない | `echo "x" > new.txt` のようなコマンドだと、確認なしで新しいファイルができる | `"matcher": "Bash"` の hook を作り、コマンドの中身を調べる |
| `Read(...)` の deny は、コマンドでの読み取りを止めない | `cat .env` のようなコマンドで読まれることがある（第5章で体験した） | CLAUDE.md でお願いしておく。Bash の hook で、コマンドに `.env` が含まれていたら止める |
| permissions は、コマンドの書き方どおりに判定する | 書き方を変えたコマンド（例: `bash -c "..."` の中に入れる）には一致しないことがある | 大事なものは hook でも調べる |
| permissions と hooks が効くのは、Claude が実行するときだけ | VS Code のボタンや、自分でターミナルに打ったコマンドは止まらない | Git の hook や、GitHub のブランチ保護など、別の仕組みを使う |
| 作業フォルダの外への読み書きは「確認」で止まるだけ | 承認すれば、外のファイルにも触れる | 確認ダイアログの内容をよく読む。プロジェクトのフォルダを 1 つずつ開く |
| `paths` 付きの rules は `/context` に表示されない | 読み込まれたかが見えにくい | 書かれた結果で確かめる（第2章の目印のルール） |

> 💡 Mac・Linux・WSL2 では、**サンドボックス**（`/sandbox`）を使うと、Bash のコマンドが読み書きできる場所を OS のレベルで制限できる。上の「コマンドでの読み取り」などの抜け穴をふさげる。Windows（WSL2 を使わない場合）では使えない。
>
> 出典: https://code.claude.com/docs/en/sandboxing

## 4. 豆知識

### 設定ファイルを英語にすると、トークンが減る

この教材では、わかりやすさを優先して設定ファイルを日本語で書いた。日本語は英語より多くのトークンを使うので、CLAUDE.md のように**毎回読み込まれるファイルが長くなってきたら**、英語で書くとトークンを減らせる。Claude は英語で書いた指示でも、日本語で答えるように書いておけば日本語で答える。

### OS による違い

| 項目 | Windows | Mac |
|---|---|---|
| hook の `command` | `python`（`python3` がないことが多い） | `python3`（`python` がないことが多い） |
| permissions | `Bash(...)` と `PowerShell(...)` の両方に書く | `Bash(...)` だけでよい |
| hook を実行するシェル | Git Bash（なければ PowerShell） | sh |
| サンドボックス | 使えない（WSL2 なら使える） | 使える |
| settings.json の中のパス | `\` を `/` に置き換えて書く | そのまま |

### 確認に使うコマンド

| 確かめたいこと | やり方 |
|---|---|
| 読み込まれている CLAUDE.md | `/context`（Memory files） |
| 読み込まれている settings.json | `/status`（Setting sources） |
| 登録されている hook | `/hooks` |
| 使える skill | `/` を入力 |
| 使えるサブエージェント | 「今使えるサブエージェントを一覧にして」と頼む |

## 5. 次にやること

- **プロジェクトごとの設定を作る**: チームで共有したいルール（使っている言語の書き方、テストの書き方）や、ファイルを書いた後に整形する hook（第6章のよくある疑問）を、そのプロジェクトの `.claude/` に置いて Git で共有する。
- **導入を自動化する**: 設定の本体を 1 つのフォルダにまとめて Git で管理し、`~/.claude/` へのコピーと settings.json への追記をスクリプトにする（第7章のよくある疑問）。
- **少しずつ育てる**: Claude に同じお願いを何度もしていると気づいたら、それが CLAUDE.md・rules・skills にするタイミング。第8章の早見表で、どれに書くかを決める。
