# 第4章 agents — 作業を任せる別の Claude

## 1. この章のゴール

サブエージェントを作って、別のコンテキストで作業させ、結果だけを受け取れる。

## 2. しくみ

サブエージェントは、**作業を丸ごと任せられる別の Claude**。メインの会話とは別の場所（コンテキスト）で作業し、**結果だけ**を返してくる。

```text
メインの会話（あなた ⇄ Claude）
   │「reviewer で score.py を見て」
   ▼
Claude: 任せる内容を書いて、サブエージェントに渡す
   │
   ▼
┌───────── サブエージェント（別のコンテキスト）─────────┐
│ 受け取るもの:   reviewer.md の本文（役割）              │
│                 任された内容、CLAUDE.md                 │
│ 受け取らないもの: これまでの会話、読んだファイル        │
│                                                        │
│ score.py を読む → 問題を探す → 結果をまとめる           │ ← この作業の中身は
└────────────────────────────────────────────────────────┘    メインに残らない
   │ 結果だけを返す
   ▼
メインの会話: レビュー結果だけが追加される
```

| 項目 | 内容 |
|---|---|
| 置き場所 | `.claude/agents/<名前>.md`（そのプロジェクトだけ）、`~/.claude/agents/<名前>.md`（すべてのプロジェクト。第7章） |
| 呼ばれるとき | 名前を出して頼んだとき、または Claude が description を見て「任せるべき」と判断したとき |
| 会話の流れ | **知らない**。任された内容と CLAUDE.md だけを見て作業する |
| 使えるツール | `tools` で制限できる（例: 読み取りだけにする） |
| トークンへの影響 | 途中で読んだファイルなどはメインに残らないので、メインの会話が膨らまない |
| 強さ | **お願い**。本文は Claude への指示。ただし `tools` の制限は Claude Code が強制する |

出典: https://code.claude.com/docs/en/sub-agents

## 3. 作ってみる

作るもの: `~/claude-practice/.claude/agents/reviewer.md`

1. 練習用フォルダの中に `.claude/agents/` フォルダを作る（`~/claude-practice/.claude/agents/`）。
2. その中に `reviewer.md` を作り、次の内容を書く（完成例: [examples/04-agents/.claude/agents/reviewer.md](../examples/04-agents/.claude/agents/reviewer.md)）。

```markdown
---
name: reviewer
description: コードをレビューする。バグ・読みやすさ・テストの3つの観点で指摘する。コードを書いた後や、レビューを頼まれたときに使う。
tools: Read, Grep, Glob
model: inherit
---

あなたはコードレビュー担当。読み取り専用で、ファイルは編集しない。

次の3つの観点で、指定されたコードを見る。
1. バグ: 空・null・0・境界値のときの動き、エラーになるケース
2. 読みやすさ: 名前がわかりやすいか、重複や長すぎる関数がないか
3. テスト: このコードを確かめるのに必要なテストケース（正常・異常・境界値）を挙げる

次の形で返す。
- 指摘: `[高/中/低] ファイル:行 — 問題 → 直し方`
- 足りないテストケース: 箇条書き
- 確認できなかったこと: 仕様がわからず判断できない点は、推測せずに質問として書く
```

| 部分 | 意味 |
|---|---|
| `name` | サブエージェントの名前。「reviewer で〜」と頼むときに使う |
| `description` | **Claude が自動で任せるかを判断する材料**。「何をするか」と「いつ使うか」を書く |
| `tools` | 使えるツール。`Read, Grep, Glob` だけなので、ファイルを書き換えたり、コマンドを実行したりできない。書かないと、すべてのツールが使える |
| `model` | 使うモデル。`inherit` はメインの会話と同じモデル。`sonnet`・`haiku` にすると、安いモデルでトークンや使用量を節約できる |
| 本文 | サブエージェントの役割。メインの会話の流れは知らないので、ここに必要なことを書いておく |

3. レビューさせるファイルを用意する。[examples/04-agents/score.py](../examples/04-agents/score.py) を、練習用フォルダの直下にコピーする（`~/claude-practice/score.py`）。わざと問題を仕込んである短いコードなので、中身は直さずにそのまま使う。

4. 保存したら、Claude Code で**新しいセッション**を開く。

## 4. 試してみる

| # | やること | 成功したときの結果 |
|---|---|---|
| 1 | 「今使えるサブエージェントを一覧にして」と頼む | 一覧に `reviewer` が含まれる |
| 2 | 「reviewer で score.py を見て」と頼む | サブエージェントが動いた表示が出て、下の表のような指摘が返ってくる |

score.py には、次の問題を仕込んである。全部、またはほとんどが指摘されれば成功。

| 観点 | 仕込んだ問題 | 期待する指摘 |
|---|---|---|
| バグ | `average([])` で 0 で割ってしまう | 空のリストで `ZeroDivisionError` になる |
| 読みやすさ | 関数名 `f` と引数 `x` | 何を表すかわからない。`to_grades(scores)` のような名前にする |
| テスト | テストがない | 必要なテストケースの一覧（空のリスト、80 点ちょうど・60 点ちょうど など） |
| 仕様 | 80 点ちょうどは A か B か | 仕様がないと判断できない → 「確認できなかったこと」に質問として出る |

> 💡 出力の細かい内容は、実行するたびに変わる。`~/.claude/` に自分の設定（CLAUDE.md や rules）がある人は、その影響も受ける（サブエージェントも CLAUDE.md や rules を読み込むため）。仕込んだ 4 つの問題が指摘されていれば成功。範囲外の点数（-5 や 150）、型ヒントがない、など、ほかの指摘が出てもよい。

**比べてみる**（任意）: 新しいセッションで、reviewer を使わずに「score.py をレビューして」と頼む。どちらも結果は出るが、reviewer を使ったときは、score.py を読んだ中身がメインの会話に残らない。読むファイルが多い作業ほど、この違いが大きくなる。

## 5. よくある疑問

<details>
<summary>Q. agents と skills は、どう使い分ける？</summary>

違いは**どこで作業するか**。

```text
skills: メインの会話の中で作業する
   → 途中の様子が全部見える。そのかわり会話がどんどん長くなる

agents: 別のコンテキストで作業して、結果だけ持ち帰る
   → 会話は短いまま。そのかわり途中の様子は見えない
```

| | skills | agents |
|---|---|---|
| 作業する場所 | メインの会話の中 | 別のコンテキスト（結果だけ戻る） |
| 会話の流れを知っているか | 知っている | 知らない |
| 使えるツールの制限 | 限定的 | `tools` で制限できる |
| 向いている作業 | 進め方を変えたいとき（説明の形・質問の仕方） | たくさん読んで、結論だけ欲しいとき（レビュー・調査） |

迷ったときは次の順に考える。

```text
途中の様子を見たい？ 会話しながら進めたい？
  ├─ はい → skills
  └─ いいえ（結論だけ欲しい）
        └─ 読む量が多い・先入観なく見てほしい・ツールを制限したい
              ├─ どれかに当てはまる → agents
              └─ どれも当てはまらない → skills で十分
```
</details>

<details>
<summary>Q. 全部 skills で作ったらまずい？</summary>

まずくはない。個人で使う範囲なら、ほとんどは skills で足りる。agents にする意味があるのは、次のどれかに当てはまる作業だけ。

1. **たくさん読むけれど、欲しいのは結論だけ**（会話を膨らませたくない）
2. **先入観のない目で見てほしい**（レビューなど）
3. **使えるツールを制限したい**（読み取りだけにするなど）

レビューは 3 つすべてに当てはまる。特に 2 が大事で、skills でレビューすると、**自分で書いたコードを自分でレビュー**することになり、書いたときの考えを引きずって見落としやすい。会話の流れを知らない reviewer なら、先入観なく見られる。

まずは skills で作り、「会話が重い」「自分で書いたものを自分でレビューしていて頼りない」と感じたら agents にする、という順番でもよい。
</details>

<details>
<summary>Q. 設計書（仕様書）がないと、きちんとレビューできないのでは？</summary>

そのとおり。レビューには 2 つのレベルがある。

| レベル | 見ること | 必要なもの |
|---|---|---|
| コードとして正しいか | バグ・読みやすさ・テストがあるか | コードだけ |
| 仕様どおりか | 決められたとおりに動くか（80 点は A か B か、など） | コード＋設計書 |

設計書がないまま仕様どおりかを見させると、Claude はコードから「たぶんこういう意図だろう」と**推測**してレビューする。推測が外れると、本当のバグを見逃す。

そこで reviewer.md には「仕様がわからず判断できない点は、推測せずに質問として書く」と書いておいた。score.py の「80 点ちょうど」がその例。設計書がある場合は、「reviewer で score.py を見て。仕様は docs/spec.md」のように一緒に渡す。
</details>

<details>
<summary>Q. 頼んでいないのに、Claude がサブエージェントを使うことがある</summary>

Claude は description を見て、合う作業なら自分の判断でサブエージェントに任せる。reviewer の description に「コードを書いた後に使う」と書いてあるので、コードを書いた後に自動で使われることがある。自動で使ってほしくない場合は、description から「いつ使うか」の部分を消す。
</details>

## 6. 自分用に変える

次のどれかをやってみる。

- **観点を 1 つ足す**。例:「4. セキュリティ: パスワードや API キーがコードに直接書かれていないか」
- **モデルを変える**。`model: haiku` にして、結果の質と速さがどう変わるかを比べる
- **別のサブエージェントを作る**。例: `explainer.md`（指定したフォルダのコードを読んで、全体の構成を説明する。`tools: Read, Grep, Glob`）

## 7. 確認問題

<details>
<summary>Q1. サブエージェントは、メインの会話でそれまでに話した内容を知っている？</summary>

知らない。受け取るのは、自分の .md の本文（役割）、Claude から任された内容、CLAUDE.md だけ。だから、必要なことは本文に書いておくか、頼むときに伝える。
</details>

<details>
<summary>Q2. reviewer の `tools` を `Read, Grep, Glob` だけにしたのはなぜ？</summary>

レビューのついでにファイルを書き換えたり、コマンドを実行したりしないように、読み取り専用にするため。`tools` の制限は Claude Code が強制するので、本文に「編集しない」と書くより確実。
</details>

<details>
<summary>Q3. 「この関数の書き方を一緒に考えたい」。skills と agents のどちらが向いている？</summary>

skills（または普通に会話する）。一緒に考えるには、途中の様子を見ながら会話を続ける必要がある。agents は結果だけを返すので、やりとりしながら進める作業には向かない。
</details>
